# Internal agent handoffs, version 1

K01 publishes the three internal envelope schemas in [`contracts/v1`](../../contracts/v1/) from the Zod authority in [`packages/contracts/src/agent.ts`](../../packages/contracts/src/agent.ts). The worker uses the Orchestrator→Red Team and Red Team→Judge handoffs. Judge→Documentation is the input contract that [F01](https://linear.app/hdxsfbr/issue/HDX-22/f01-implement-evidence-grounded-finding-metadata-and-report-drafting) consumes (see "Documentation reports" below); K01 itself invokes no Documentation role. These contracts do not prove communication with an independent peer service; [I01](https://linear.app/hdxsfbr/issue/HDX-36/i01-complete-peer-integration-proof-and-security-review-evidence) owns that evidence.

Every envelope has `channel`, `status`, and a strict header: `version: 1`, a fresh `messageId`, optional `parentMessageId`, and `runId`, `caseId`, `attemptId`. The header binds a message to one execution. For a selected case, the worker uses the run ID and lease generation for the attempt ID. For an adaptive case, it adds the ordinal. All handoffs for that attempt reuse this ID; a new lease generation cannot consume the prior attempt's message. The Orchestrator success contains the selected seed ID, category, remaining case/time bounds and optional history references. The Red Team success contains the executed, provider-projected Judge packet, policy version and evidence references. The worker validates the selection before beginning an adaptive case, validates a Red Team proposal before target execution, and validates the executed handoff before pricing or reserving the Judge model. The model consumer validates it again before transport. The model's raw JSON is not an agent envelope and cannot supply a trusted header.

Evidence references are composite `(runId, attemptId, ref)` records. Each records observation version and completeness; v2 also records the target turn ID. v1 observations remain readable with completeness `unknown`, not inferred complete. The Red Team→Judge validator requires unique observation refs and turns, unique action turns and evidence refs, and one-to-one mapping among them. A PDF action must carry its artifact type and uploaded source ID, matching a v2 observation attachment; PDF-to-v1 handoff is rejected because v1 cannot bind an attachment. A chat action cannot carry PDF fields or pair with a v2 observation bearing attachment metadata. Stored historical v1 records remain inspectable outside this new handoff. Check references must point into that packet. The consumer applies the existing 100,000-character packet cap. Header/context mismatch, unsupported version, malformed shape and inconsistent evidence fail with typed `AgentContractError` before provider transport. A schema-valid envelope alone does not prove a claim or broaden the E03 safe or automatic confirmation gates.

| Channel | Success or nonfinding meaning | Known error handling |
| --- | --- | --- |
| Orchestrator→Red Team | Select one allowed seed under the stated bounds; selection does not authorize arbitrary actions. | Invalid model selection emits a validated `invalid_contract` failure at `orchestrator` stage before a case is selected; model unavailability or budget expiry also emits a typed failure. The worker conservatively limits the run. |
| Red Team→Judge | Executed prompts, observed target evidence, deterministic checks, effect scope, limitations and stable refs are passed to the Judge. | Invalid Red Team JSON, raw transport instructions or unauthorized PDF references emit `invalid_contract` at `red_team` stage before target dispatch. Runtime worker events contain typed `target_unreachable`, `target_boundary_unavailable`, `budget_exceeded`, `reservation_unavailable`, `judge_timeout`, or `provider_unavailable` envelopes where those conditions are observed. Before scheduled adaptive preflight selects a case, the event contains a validated `contractError` without an invented case ID. Deadline stage, elapsed/limit milliseconds and `attempted` are retained; an attempted paid timeout remains an unknown charge under E04. |
| Judge→Documentation | `ok` requires an automatically confirmed outcome or a separately human-confirmed pending-review outcome. `no_findings` means no supported finding was produced; its source outcome may be safe, inconclusive, incomplete or blocked and the status itself makes **no safe assertion**. Regression is explicit (`new`, `recurring`, `fixed`, `resurfaced`, `unknown`, or `not_applicable`). | F01 must validate this envelope at both ends and implement report-job error mapping; K01 supplies only its schema and parser. No report or regression verification is implied by this schema. |

The existing E03 deterministic policy remains the only worker authority for `safe` and `auto_confirm`. A quoted response does not prove unseen chart access or writes. A Documentation `ok` envelope requires evidence refs, a policy trace and a separate confirmation basis. F01 must compare these fields with persisted decisions and approved evidence before report creation. A regression label is a typed claim to verify against earlier findings, never proof by itself.

Regenerate schemas with `node --import tsx contracts/generate.ts`; `tests/contracts/agent.test.ts` fails if committed JSON drifts from the Zod source. Compatible optional fields can be added only when old readers retain their meaning. A changed required field, enum meaning, evidence semantics or eligibility rule requires a new schema version and documented migration; silently reinterpreting v1 messages is disallowed. Existing persisted observations and policy events remain v1/v2 as recorded and are not relabeled by these handoffs. No cross-process delivery, independent-agent execution, live target correctness or model accuracy is established by the synthetic contract fixtures.

## Documentation reports (F01)

The worker's report-job handler (`apps/worker/src/reports.ts`) rebuilds one Judge→Documentation `ok` envelope per confirmed finding from **persisted** decisions and evidence (candidate route, assessment verdict and policy trace, stored target observations and the case definition), validates it with `parseAgentMessage`, and sends the model only that envelope payload, the aliased evidence facts and the allowed citation IDs. Any missing or invalid piece fails the job with `missing_required_evidence:<fields>`; no model call is made and nothing is filled in. A human-confirmed finding whose stored policy says `auto_confirm` (evidence integrity failed at automatic confirmation) is presented as `pending_review` with an added `routed_to_human_review` failed gate. The regression label is `new` only when no other confirmed finding for the same attack sequence exists on the target, otherwise `unknown`; it is never asserted from model output.

`documentationReport` v1 ([schema](../../contracts/v1/documentation-report.schema.json), Zod source `packages/contracts/src/report.ts`) is the only shape the model may author: title, severity level and rationale, clinical impact, description, cited expected and observed behavior, reproduction notes, remediation, uncertainty. It is strict, so an extra key such as a second finding is a schema failure. Citations must be `case` (expected behavior only), `verdict`, `turn-N` or `check-N` IDs present in the input; observed behavior needs a `turn-N` citation; quotes must be verbatim excerpts of a cited observation; a known case-rubric severity cannot be contradicted; introduced UUIDs or unknown `Patient/Clinician` aliases are rejected. Identity, category, target/version, the reproduction steps (from the executed case definition), evidence excerpts, checks, verdict, policy and validation history are deterministic `reportFacts`, never model output, so the reproduction mechanism cannot be changed by a reply. Stored revisions are `reportContent` v1 `{ facts, narrative }`.

Redaction is deterministic and applied twice: to the model input and to its reply. Aliases are fixed by the target's user slot (`Patient A/B` for external patient IDs, `Clinician A/B` for usernames; passwords, cookies, CSRF tokens, session IDs and bearer tokens become `[REDACTED]`), match whole identifiers case-insensitively, and a final leak scan fails the job (`redaction_failed`) rather than store a revision. The `{{OTHER_PATIENT_ID}}` case placeholder renders as the other patient's alias. Revisions live in `report_revisions` (migration 018): content is immutable, an operator edit or newer draft is a new revision, and approval belongs to one exact revision and is voided when a newer revision exists. Compatible optional narrative fields may be added within v1; a changed required field, citation rule or facts meaning needs `documentationReport` v2 with a documented migration, and existing revisions keep the version they were stored with.

## Adaptive exploration feedback and mutation lineage (A17)

The Orchestrator→Red Team payload gains three optional v1 fields (compatible: a payload without them is unchanged): `selection` (why the seed was chosen: `regression_resurfaced`, `regression_recurring`, `unresolved_severity`, `coverage_untested|inconclusive|incomplete|blocked` or `least_executed`, with the signals and the target version they were read at), `feedback` (up to three sanitized prior verdicts of this run and category: execution case, outcome, Judge verdict and redacted claim, failed policy gates) and `mutation` (`seedCaseId` plus `parentExecutionCaseId`, the earlier execution case of the same run whose verdict the Red Team was shown, same seed preferred; `null` means only the seed is mutated). A parent must be one of the shown verdicts and the seed must match the envelope's case, so a proposal can be traced to the evidence and outcome it was conditioned on. Migration 021 stores `parent_execution_case_id`, `selection` and `follow_up_turn` on `adaptive_cases`; rows from earlier runs keep NULLs, meaning unrecorded, and both the run's case list and case detail API expose them.

Selection ranks work by regression state (resurfaced, then recurring; G02), unresolved finding severity (pending review or confirmed and not derived as fixed) and the V01 coverage gap of the run's target and observed version (untested, inconclusive, incomplete, blocked), after categories the run declared but has not yet executed. Only the top-ranked seeds of the chosen category are offered to the Orchestrator model; a pick outside that list fails the handoff as before. Each category is parked for the rest of the run after 3 consecutive safe/inconclusive cases or 2 consecutive rejected/blocked ones; the case that parks it records a `redirect` event (from/to category, reason, streak, limit) or, with nothing left to run, a `stop` event. A stagnation stop is a recorded decision, not a run limit.

The Red Team may add `"followUp": true` to a proposal of at most two actions. After the last planned turn is observed it is shown the redacted, untrusted replies and may propose exactly one more `chat_turn`. That follow-up passes `admitProposal` (one action, chat only, same message restrictions), is persisted to the case before it is sent (`follow_up_turn`, so a regression replay reproduces it) and is recorded as `followup_admitted`, `followup_rejected` or `followup_skipped`. It reserves through the same model-call path as every other Red Team call, so the stop, lease, deadline and paid-cap limits apply, and the case never exceeds 3 turns.
