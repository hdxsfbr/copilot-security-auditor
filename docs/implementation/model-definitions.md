# Model preflight and reusable run definitions

M01 validates the roles the current execution invokes. A selected run invokes only Judge. An adaptive run can invoke Orchestrator, Red Team and Judge. Documentation remains inactive until its report job is implemented. Historical four-role inputs remain readable; new inputs project away inactive assignments before availability, pricing and execution checks. A selected legacy `model` field means a local Judge. A paid-only definition does not need an Ollama URL; a local active role does.

`GET /api/models` retains `openrouter`, `ollama` and `configured` for existing clients and adds provider `availability` (`available`, `unavailable`, `not_configured`) and `inferenceHealth: "unverified"`. An available catalog can be empty. Discovery verifies that a model name is listed; it does not execute inference or prove health. `POST /api/model-preflight` accepts `{kind:"selected"|"adaptive",input:...}` and returns typed issues, local/paid catalog status, `inferenceHealth`, and a reservation preview. No model call or target call occurs. An unavailable catalog or unverifiable paid price returns an unavailable result with unknown paid cost, never a zero-cost assurance. A local-only preview of zero paid reservation says nothing about local inference health.

The preview is a worst-case *reservation* using the catalog's verified per-token/request dimensions and the full context length. A selected run reserves at most one Judge call. The current adaptive loop has `maxCases` outer attempts; each attempt invokes at most one Orchestrator, one Red Team and one Judge, even if a proposal is rejected. There is no provider retry in that loop. Accordingly, preview sums the active role reserves and multiplies by `maxCases`. The cap can stop execution earlier, and the estimate is neither a charge prediction nor a promise that dispatch will succeed. Worker dispatch still refreshes paid prices, reserves under the ledger, and holds uncertain charges as before.

`POST /api/run-definitions` stores `{name,run:{kind,input}}` as one reusable definition. `GET /api/run-definitions` lists current definitions; `GET /api/run-definitions/:id` includes its revision. `PUT /api/run-definitions/:id` requires `{revision,name,run}` and rejects stale revisions with 409. `DELETE /api/run-definitions/:id` requires `{revision}` and archives the template. `POST /api/run-definitions/:id/launch` requires `{revision}`, resolves and copies that exact version, preflights it, then uses the normal target reservation path. Schedule creation/update may submit its existing inline `run` or `{runDefinitionId,revision}` in place of it. The latter resolves and copies the canonical inline run input into `schedules.definition` and `schedules.run_snapshot`; schedule ticks never dereference a mutable template.

Each launch keeps the existing immutable target, case/version, model/pricing and bound snapshots in `runs`. Editing or archiving a template cannot change queued or historical runs, schedules already saved, or their occurrences. The definition revision protects a user who loaded an older template from silently launching or scheduling a newer edit. It does not change the existing schedule edit/delete semantics.
