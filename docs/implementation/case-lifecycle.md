# Case lifecycle (C01)

The versioned authoring path is `POST /api/cases/drafts` → upload PDFs to `/api/cases/:id/artifacts?documentType=...` → `PUT /api/cases/drafts/:id` → `POST /api/cases/drafts/:id/publish`. A failed upload or publish leaves the draft listed at `GET /api/cases/drafts`; it cannot be selected for a run or schedule. Drafts accept incomplete definitions so an operator can save a title before authoring actions or uploading a PDF. Publishing requires a complete definition, 1–3 actions, at most six checks, category, and version 1 rubric metadata. It verifies every referenced PDF's case linkage, document type, byte count, and SHA-256 against the stored file. Restore a missing/corrupt file or upload a replacement and update the draft before retrying.

`POST /api/cases/:id/clone` creates the next draft version in the same family. It copies verified PDFs into new artifact IDs and rewrites the cloned action references. A copy failure returns `artifact_copy_failed` and a recoverable `draftId`; the original version and any run snapshot stay unchanged. A draft update during the copy wins: the clone finalization uses a compare-and-set guard and will not overwrite that edit. `GET /api/cases/:id/versions` accepts any version ID, and `GET /api/cases/:id/executions` links observed run results to the selected definition version. `POST /api/cases/:id/archive` removes that version from the runnable catalog. Selected, adaptive, scheduled, and regression replay selection require a published version. Existing runs, events, and snapshots remain historical records.

`GET /api/cases/:id` and the version list expose `state`, `authoringMode`, `version`, `familyId`, publication/archive timestamps, and `metadataStatus` (`complete`, `incomplete_draft`, or `unknown_legacy`). Migration 010 marks old cases as published version 1 with `authoringMode: legacy`; absent category or rubric fields remain absent. The API never invents historical OWASP mappings, exploitability, or boundary rationale. Cloning an old case retains those gaps in a draft; an operator must complete the rubric before publishing the new version.

The old `POST /api/cases` text-case flow remains available for the current UI. Its PDF flow still creates a runnable legacy text case before uploading, so a failed PDF upload in that UI is **not yet covered** by the new draft guarantee. C02 must switch that UI to the draft route. Legacy `PUT /api/cases/:id` remains limited to a legacy published case that has no run, adaptive seed, replay, or active schedule reference. Once referenced, it conflicts. Versioned published cases cannot be edited through either update route. The old catalog `GET /api/cases` lists published cases so the existing launchers continue to work while the case workspace migrates.
