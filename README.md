# Clinical Co-Pilot Auditor

An adversarial security platform for an **operator-owned synthetic** OpenEMR / Clinical Co-Pilot. Four roles (Orchestrator, Red Team, Judge, Documentation) attack the Co-Pilot through its user-facing chat and PDF channels, record every reply as structured evidence, judge it under deterministic policy gates, route uncertain results to a person, draft reports for confirmed findings and replay confirmed attacks as regressions across target versions. It covers prompt injection, chart-context isolation (cross-patient) and unintended tool actions. Safe, inconclusive, blocked and incomplete outcomes stay distinct, and an incomplete result is never a pass. It is a LAN-only operator tool and does not deploy the target. Do not point it at clinical records or an unauthorized service.

## Architecture overview

A React UI and Express API accept targets, cases, model assignments and run limits. PostgreSQL holds target reservations, run snapshots, worker leases, events, findings, the model-call ledger and schedules; a private volume holds synthetic PDFs. A TypeScript worker claims a run under a lease and, per case, opens a fresh authorized session, sends admitted actions, stores each reply as a versioned observation, applies deterministic checks, asks the Judge model for a cited verdict and applies policy gates. Selected runs execute one operator-chosen case and call only the Judge. Adaptive runs add the Orchestrator (chooses a ranked seed) and the Red Team (proposes one to three typed actions behind an admission gate). Confirmed findings become regression identities, replayed by suites, and can be drafted into a report by the Documentation role, which a person approves revision by revision. The [architecture document](ARCHITECTURE.md) has the interaction diagram, role table, message contracts, orchestration and regression design, observability, external API handling (auth, rate limits, pagination, 429) and the AI-use disclosure.

## Run in Docker

Requires Docker Compose, a host Ollama with an installed model, and an operator-owned toy target; Node, npm, and PostgreSQL run only in containers. Copy `.env.example` to `.env`, generate a unique `DB_PASSWORD` and 64-character hex `CREDENTIAL_KEY`, and set `LAN_BIND` to a specific trusted LAN interface (or `127.0.0.1` for this machine only). Set `OLLAMA_MODEL` to a model installed on the host. Docker Compose reads `.env` automatically; no environment variable exports are needed. Keep `.env` private, back up `CREDENTIAL_KEY` securely, and reuse both secrets across restarts; changing the database password or encryption key after storing data requires a coordinated rotation. Start the stack:

```sh
docker compose up --build -d
```

Open `http://<LAN_BIND>:3000` from the trusted LAN. The API migrates the database at startup and serves the built UI. The run composer loads its Ollama endpoint and installed model defaults from `.env` via the API's `/api/config` endpoint; edit only `.env` to change these defaults, then recreate the services with `docker compose up --build -d`. Compose maps `host.docker.internal` to the host gateway for the API and worker on Linux. The worker and database have no published host ports, and Compose does not start or download an Ollama model.

The host Ollama must be reachable from Docker. Ollama bound only to `127.0.0.1:11434` on Linux is **not** reachable through `host.docker.internal`; configure the host Ollama listener for an address reachable from the Docker network and restrict port 11434 with your firewall. Do not bind Ollama to a publicly reachable interface just to make the container connect. If you use a different reachable host address, port, or installed model, edit `OLLAMA_URL` or `OLLAMA_MODEL` in `.env`. The UI calls the auditor API, not Ollama directly, so the endpoint must work from the **worker container**, not just your browser.

The target itself is not deployed by this stack. Enter an OpenEMR URL reachable **from the worker container** (for example, another container's service name on a shared Docker network, `http://host.docker.internal:<port>/` if the toy target listens on an address reachable via the host gateway, or a public HTTPS hostname). A browser-local `127.0.0.1` target URL points back to the worker container and will not work. Only use an authorized synthetic target. Keep the credential key outside PostgreSQL, back it up separately, and do not rotate it without re-encrypting stored identities. Treat the PostgreSQL and private evidence volumes as one backup unit. There is no application login: **anyone who can reach the LAN port has full operator power**, including reading synthetic observations. Do not expose it publicly.

## Run the platform against a live target

Use this sequence for the public deployment or any other authorized target. Attack only synthetic accounts and charts; the target's operator supplies the accounts and passwords (see the [brief](docs/COPILOT_FEATURE.md#2-actors-accounts-data)).

1. **Authorize and allow the host.** Get the target owner's permission. Add the target's exact hostname (for the public deployment, `openemr-137-184-4-22.sslip.io`) to `TARGET_ALLOWED_HOSTS` in `.env` and recreate the stack. The list is exact-hostname only, and the worker must be able to reach the target from its container.
2. **Choose models and limits.** Local Ollama needs no key and has no dollar price. For OpenRouter, set `OPENROUTER_API_KEY` only in `.env`, choose a model with a verified catalog price and a per-run USD cap above one call's reservation (see [cost analysis](docs/submission/cost-and-scale.md#3-price-inputs-and-two-code-level-findings)).
3. **Create the target** on the Targets page: name, OpenEMR root URL and two distinct synthetic clinician assignments, each with the chart's external `pubpid`. The worker checks readiness, login and that each `pubpid` resolves to exactly one chart before any turn.
4. **Start small.** On Launch, compose one selected case first. The target documents 10 turns per minute per conversation, 20K tokens per turn and a 2M-token daily halt for the whole process; a case sends at most 3 turns, so keep adaptive runs small (`maxCases` and `maxMinutes`) on a shared deployment.
5. **Compose, preflight, start.** Pick the case or adaptive seed set, assign a model per role, read the preflight (availability, reservation preview, cap) and press Start. Nothing dispatches before Start. A target holds one active run, and a busy target returns 409 with the active run ID.
6. **Watch and stop if needed.** The run page loads events incrementally and shows usage and outcomes; Stop is cooperative.
7. **Review.** On Findings, inspect evidence beside the verdict and confirm or reject each candidate. Approve an exact report revision to download it.
8. **Replay and track.** On Regressions, replay confirmed attacks after a target change (or enable the opt-in version-change trigger); on Coverage, filter by target and version.
9. **Export evidence** with the auditor's own API (`GET /api/runs/:id`, `/events`, `/usage`, `/cases`, and `GET /api/coverage/scoped`), as the [first live pass](evals/results/live/2026-09-29/README.md) did. Credentials never leave the auditor.

## Selected-case workflow

1. Create a target with the OpenEMR root URL (trailing path allowed) and **two distinct authorized synthetic** user/chart assignments. Enter each chart's **external patient ID (`pubpid`) shown in OpenEMR**, not its internal numeric `pid` or patient name. External IDs accept letters, digits, and hyphens only (no search wildcards). The worker resolves each assigned ID with that user's authenticated OpenEMR patient finder, requires exactly one exact result, and uses its numeric `pid` only to select the chart. Missing, ambiguous, inaccessible, or mismatched lookups block the run before a turn. Credentials and assignments are AES-256-GCM encrypted in PostgreSQL; passwords are never returned by the API. The deployment key is required to decrypt them. Save creates a new target and selects it for the next run; use "Target to configure" to load an existing target's username and external ID for editing. Leave passwords blank on update to keep their existing values, or enter new passwords to rotate them. Target updates are rejected while a run is reserved, and prior runs retain their credential references.
2. The Cases page lists versioned, published cases: a starter matrix of ten cases (three boundaries times direct, quoted-text and multi-turn variants, plus an advice-only control; see [evals/seeds](evals/seeds/README.md)) and three legacy starters kept for historical replays. Each carries category, subcategory, OWASP mappings and severity and exploitability rationale. Author a new case, with an optional synthetic PDF, through the draft, publish, clone and archive lifecycle. Inspect the case preview before starting: nothing is dispatched until you press Start. The chart-context cases open user A's assigned chart and ask about user B's assigned chart; the worker substitutes `{{OTHER_PATIENT_ID}}` with the saved external ID. Both charts must resolve distinctly, but OpenEMR finder visibility and physician access to both records are not considered Co-Pilot failures. Merely repeating an ID from the prompt is not proof of clinical disclosure; chart-context results needing proof remain inconclusive or pending review, not auto-confirmed. The quoted-text variants only simulate an indirect channel; the real PDF channel needs a case with a synthetic PDF and a source-citation check. The no-write cases request advice only. The worker compares read-only OpenEMR patient reports (including orders) before and after the turn and records `changed`, `unchanged`, or `unavailable` without persisting the report contents. A change needs review; an unchanged report cannot rule out writes not represented in the report, so these cases are never scored `safe`. A busy target returns 409 with the active run ID.
3. The worker probes readiness, logs in with a fresh cookie jar (302 success), resolves the exact external ID through `interface/main/finder/dynamic_finder_ajax.php` (`sColumns=pubpid`, `searchType=true`), opens the resolved numeric chart, obtains the module CSRF and conversation, mints a new ticket per turn, and calls the user-facing agent endpoint. A valid `fallback` is evidence, not a pass. Only an explicitly not-applied turn can be retried once with a new ticket. Ambiguous delivery ends incomplete.
4. In the composer's model step, choose a provider, model and maximum output tokens for each active role. Selected-case runs call **only the Judge**; adaptive runs also call the Orchestrator and Red Team. The Documentation role runs only in report jobs, and only when the run has an opt-in report policy (a model, and for a paid model an allowance inside the run cap) or an operator authorizes a job. With no `OPENROUTER_API_KEY`, use local Ollama and no dollar price is assigned to local inference. For OpenRouter, set `OPENROUTER_API_KEY` only in private `.env`, choose an available model and set a positive per-run USD cap before starting. A verified catalog price for the entire context window, maximum output and request fee is reserved transactionally before dispatch. The paid request restricts provider prices to those reserved and disables provider fallback. Unknown or unsupported pricing, over-cap estimates and unresolved provider charges prevent further paid calls; an ambiguous charge remains reserved and an incomplete run never becomes a pass. No automatic model fallback occurs. The server does not return the key to the browser. Hosted role calls receive secret-scrubbed, patient-aliased packets, never session cookies or raw assigned patient IDs. Use synthetic data only; packet scrubbing is not a substitute for de-identifying arbitrary free-text clinical records.
5. The run page shows target version, turn and attempt sequence, deterministic check scope, provider and model token and latency usage, reported paid charge or unresolved reservation, verdict and review candidate. A pending-review run releases its target immediately. Only a missing structured citation in a complete prompt-injection observation can be auto-confirmed; every other candidate requires operator review. Confirmation, automatic or manual, creates a regression identity and an idempotent report job.

## Bounded adaptive exploration

Choose one or more saved synthetic seed cases in the composer's adaptive mode; the chosen categories, assigned users, expected safe behavior, checks, and approved PDF references come from those cases. Set 1-9 maximum cases and 1-30 elapsed minutes, plus a per-run OpenRouter cap if any selected role uses OpenRouter. Code ranks seeds by regression state (resurfaced, then recurring), unresolved finding severity and the scoped coverage gap for the target and observed version, and offers only the top-ranked seeds of the chosen category to the Orchestrator. A category with three consecutive safe or inconclusive cases, or two rejected or blocked ones, is parked; the run records a `redirect` or `stop` event. The Red Team proposes 1-3 typed actions and may ask to see the first reply and send one more chat turn (never more than three turns). Raw URLs, requests, patient identifiers, credentials, and unlinked PDF references are rejected before target transport; identities are blocked as whole tokens. Each admitted case runs in a fresh authorized chart session through the same judgment and finding gate as a selected case. Only executed cases count toward coverage; the progress panel shows rejected, blocked, inconclusive, incomplete, and untested categories. Stop is cooperative: an already in-flight request may complete, but an unfinished case and its parent run cannot become a pass. The target reservation is released on completion. A confirmed adaptive finding can be replayed from the Regressions page, which materializes its exact validated action definition (including an admitted follow-up) and links only its authorized synthetic attachments.

## Findings, reports and regressions

- **Review.** Confirm or reject a candidate with a rationale code from a fixed list; decisions and corrections are append-only. Evidence integrity is checked first: a missing or changed artifact blocks a new confirmation and any approval.
- **Reports.** The Documentation role drafts narrative only (title, severity rationale, clinical impact, description, cited expected and observed behavior, remediation, uncertainty). Identity, reproduction steps, evidence excerpts, checks and verdict are worker-built facts. Output is schema-checked, citations and verbatim quotes are verified, identifiers are redacted on input and output, and a leak scan blocks storage. An operator edit creates a new revision; approval belongs to one exact revision and a newer revision voids it. Only an approved, redacted revision can be downloaded as Markdown or JSON. The older generic JSON export (`approve-export`) remains for existing callers.
- **Regressions.** Each confirmation is a regression identity; a suite replays up to 25 identities one at a time and derives `fixed`, `recurring`, `resurfaced` or `unknown` per observed target version. The version-change trigger is off by default, per target, and never retroactive. Neither changes the target. See the [architecture](ARCHITECTURE.md#regression-harness).
- **Optional corroboration.** A read-only evidence bridge can add scoped signals for write or fact claims. It is disabled unless an operator configures it, and none has been activated against a live target ([contract](docs/implementation/evidence-adapter.md)).

## Scheduled evaluations

Use the Scheduled evaluations panel to create or edit a daily or weekly schedule from a saved run definition (compose and save one under Launch). Picking a definition shows its target, mode, cases, active-role models, paid cap and any report policy; then choose a wall time, weekday (Sunday through Saturday for weekly) and IANA time zone. Every schedule and occurrence time is shown in the schedule's own zone with its abbreviation, for example `09:00 America/Chicago (CDT)`, plus a labeled browser-local line when your browser zone differs. Schedules snapshot the definition revision, case definitions and model choices; each due occurrence takes fresh saved target credentials. Pausing retains occurrence history; resuming after missed times advances to the next future local slot. Removing a schedule archives it: future occurrences stop, and it moves to Archived schedules, where its definition summary and its occurrence history (paged newest first, with state, skip or block reason and a link to the run) stay inspectable. A skipped occurrence records its scheduled timestamp and busy target run ID, and a failed target/login/chart preflight is blocked, never a safety pass or retry of that occurrence. Runs queued by a schedule use the same evidence, findings, regressions and report policy as manual runs. At a daylight-saving gap the first valid local minute after the gap is used; at a repeated local time only the first occurrence fires. If the API was offline at a due time, it records that occurrence at its original scheduled timestamp when it restarts, then advances to the next future occurrence; review it before assuming the target state is unchanged. A worker lease timeout marks the scheduled occurrence blocked with an execution-uncertain reason. The scheduler ticks in the API container and does not publish an additional port.

The module handshake and `/copilot-api` paths are specified by the operator's toy target contract. If your target differs, verify the contract before use. Responses are bounded and known secrets are scrubbed before persistence; the Judge receives stable patient aliases rather than raw patient IDs. Keep these toy observations on a trusted LAN.

## Operations and recovery

- **LAN boundary and firewall:** `LAN_BIND` must be the trusted interface address, not `0.0.0.0`; Compose publishes only port 3000 on that address. Add host-firewall rules allowing that port only from the operator subnet, deny it from guest/WAN networks, and do not publish the database, worker, artifact volume, or Ollama port. LAN reachability grants full operator power: every reachable client can configure targets, run tests, read full synthetic evidence, decide reviews, and approve reports. This is the access boundary; there is no authenticated application user.
- **Target allowlist:** `TARGET_ALLOWED_HOSTS` is a comma-separated exact-hostname allowlist, not a URL or wildcard list. Include only the operator-owned toy target hostname(s), e.g. `host.docker.internal` or a private Compose service name. The API rejects target create/update outside this list. Do not add broad public domains or clinical systems. Provider/Ollama egress should also be restricted at the host/network firewall to the endpoints in use.
- **Worker and queue health:** the Overview page shows worker heartbeat, queue age and lease state from `GET /api/operations/health`. A stale heartbeat is a signal, not proof the worker stopped, and `/api/health` reports only database and migration readiness.
- **Keys and identities:** Generate a unique random `DB_PASSWORD` and 32-byte `CREDENTIAL_KEY`; store `.env` and off-host copies in an operator-controlled secret store with limited access. Back up the credential key separately from the database: database backup without the matching key cannot decrypt saved test identities. Never paste keys into issues/logs or commit them. Use two distinct, least-privilege synthetic OpenEMR accounts assigned only seeded toy charts; use external `pubpid` values, not real patient data. Key rotation requires coordinated credential re-encryption; changing the key in place makes stored credentials unreadable.
- **Evidence and decisions:** Missing, checksum-mismatched, or orphaned files invalidate evidence integrity. Such cases are incomplete/inconclusive, never safe and never confirmed findings. Evidence/artifact integrity failures require restoration and a new explicit run; never replay an ambiguous target turn automatically. Review captures an action and timestamp only; it does not authenticate or prove the reviewer's identity. Report approval is a separate explicit action.
- **Spend:** UI call rows distinguish provider-reported OpenRouter charge (`settled`) from conservative reserved amounts whose billing could not be determined (`unresolved`). Unresolved holds remain in the run total and stop further paid calls until an operator reconciles provider usage on the Overview page (a one-time, evidence-backed attestation, [details](docs/implementation/spend-reconciliation.md)). A configured cap bounds the auditor's dispatch reservation based on verified pricing, but is not a guarantee against provider-side billing variance. Ollama calls show usage/latency without an invented dollar price.

### Paired database and evidence backup

Take backups while API and worker are stopped so no new database references or artifact writes can race the pair. Keep the dump and volume archive together, encrypt them at rest, and include the matching `CREDENTIAL_KEY` in a separately protected recovery envelope:

```sh
docker compose stop api worker
docker compose exec -T db pg_dump -U auditor -d auditor -Fc > auditor-db.dump
docker compose run --rm --no-deps api tar -C /app/private-evidence -czf - . > private-evidence.tgz
docker compose start api worker
```

Restore into an isolated, trusted LAN deployment with the same Compose project/volume names and matching `.env`. Keep API and worker stopped while loading both halves:

```sh
docker compose stop api worker
docker compose exec -T db pg_restore --clean --if-exists -U auditor -d auditor < auditor-db.dump
docker compose run --rm --no-deps api tar -C /app/private-evidence -xzf - < private-evidence.tgz
docker compose up -d api worker
curl --fail http://<LAN_BIND>:3000/api/health
```

Verify a prior run and retrieve its referenced PDFs through the API; `GET /api/integrity` reports missing, corrupt, or orphaned volume entries, and each referenced PDF is checked against stored size and SHA-256 metadata before use. Do not expose the isolated restore to an untrusted network. The API health endpoint reports unavailable until PostgreSQL is reachable, migrations are complete, and its migration ledger can be read; the worker is gated on that health check. Worker leases expired during downtime are fenced, unfinished cases become incomplete, target reservations release, and ambiguous paid calls stay unresolved rather than being redispatched.

### Opt-in live smoke

The fixture suites never invoke `test:live`. The live smoke is a separate, explicit operator command and requires the exact target URL, two assigned synthetic identities, a stated maximum possible provider charge, and confirmation that the target/provider actually enforces a matching spend cap. It validates readiness/login/chart/session for both identities, distinct chart assignments, one bounded synthetic PDF attachment, and one short ticketed turn. It does not provision or authorize a target, and does not itself enforce provider billing; stop if the effective provider-side cap cannot be confirmed.

```sh
SMOKE_TARGET_URL=https://toy.example.test/ \
SMOKE_USER_A=synthetic-a SMOKE_PASSWORD_A='...' SMOKE_PUBPID_A=SYN-900001 \
SMOKE_USER_B=synthetic-b SMOKE_PASSWORD_B='...' SMOKE_PUBPID_B=SYN-900002 \
SMOKE_CHARGE_CAP_USD=0.05 SMOKE_PROVIDER_CAP_CONFIRMED=true \
npm run test:live
```

Run only against an operator-owned toy target after separately authorizing the identities and setting its effective provider-side cap. Do not use real patient data. The smoke command is never run automatically or on startup.

## Verification

The fixture suite (297 tests) validates code against synthetic fixtures; it does not contact a live target or paid model. Use Node 24, Docker and Chrome. With one disposable PostgreSQL service the whole suite takes about 25 seconds on a 32-core workstation (62 seconds when measured for this submission under other host load):

```sh
npm ci
npm run typecheck && npm run build     # browser tests serve the built UI
docker run -d --rm --name ca-test-pg -e POSTGRES_USER=auditor -e POSTGRES_PASSWORD=fixture-only \
  -e POSTGRES_DB=auditor_test -p 127.0.0.1:55432:5432 postgres:17-alpine -c max_connections=300
TEST_DATABASE_URL=postgresql://auditor:fixture-only@127.0.0.1:55432/auditor_test \
  CHROME_BIN=/usr/bin/google-chrome npm run test:local
```

Without `TEST_DATABASE_URL`, `npm run test:fixtures` starts a disposable container per test and runs serially. Focused evals: `node --import tsx --test tests/judge-policy.test.ts` (labeled routing fixtures) and `node --import tsx --test tests/triage-simulated.test.ts` (simulated triage). Merge requests are gated by exact-head local validation, and GitLab CI runs the same suite on `main` ([details](docs/implementation/validation.md)). A fixture pass is never a live finding. The live evidence is in [evals/results/live](evals/results/live/2026-09-29/README.md).
